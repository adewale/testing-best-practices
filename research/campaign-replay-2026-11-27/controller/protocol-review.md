# Pre-run review of the four-arm replay

Proceed with 48 subjects and 12 judges once the controller freezes the decisions below. The nine planning cases test continuity. The three repository cases can establish whether a subject delivered and verified a useful repair in a time-boxed audit of a large suite. Record a historical source and a fault witness for each repository case. Call a case a replay of a particular failed campaign only where that link holds. A new audit finding in the same repository supports a different claim.

## Decisions to fix before the first subject

1. **Pin the four interventions and common environment.** Record the exact guidance, scripts, directory layout, versions and task packets, plus the public snapshot, dependency installation and commands for each case. Fingerprint the current PR and revised tree separately. Use the same case, source availability, entrypoint policy, writable scratch area and budget within a case. Preserve OpenClaw's relative links and its applicable guides verbatim. Map host-specific commands to the target's actual runners for everyone. A one-repair assignment exercises OpenClaw's ordinary candidate-audit path. Its exhaustive campaign, independent reviewers, upstream history and landing steps need different access and resources. Define the unaided arm as receiving project instructions and native tooling with no supplied audit package. If the revised arm alone receives an executable helper, the estimand is the revised package as delivered. For Phase A, freeze which relevant references are supplied to each arm and retain the prior task text, response format and grading rules. 2. **Publish the sampling denominator that subjects actually receive.** Agentic Mermaid supplies 58 complete conventional test files from 660 inventory paths. Keyboardia exports **all 370** conventional test files and marks 58 priority files. PDA supplies 56 of 155 first-party named test modules. Each selection deliberately includes earlier audit anchors, then fills per-stratum quotas by a deterministic hash. The underlying definitions also differ. For each cell distinguish upstream inventory, available file contents, priority sample, self-reported inspection, tests selected by a runner, and tests that actually executed. Treat claims about an entire owner's test coverage as unverified where sibling evidence is unavailable. The common CI observations and focused command guides can direct discovery. For example, Mermaid provides historical coverage annotations and a saved-answer grading command. Describe this as repository triage with supplied evidence. 3. **Freeze scoring and the allowed alternative path.** Seal the case task, sampling manifest, selection seed, identity map, success/retention criteria, control inputs, expected behavior, selection rule for submitted tests, and judging instructions before any subject sees a case. Hash or locally commit the artifacts and record the checkpoint. Assign opaque IDs and freeze the judge order independently. Give a legitimate, unanticipated repair the same absolute test as a known repair. It must identify a supported contract, show a discriminating before/after result at its owner, and retain independent behavior. A blinded reviewer can reproduce the subject's cited contrast under this rule. Record new controls as exploratory. A missing predefined issue contributes to the known-discovery count only. Subjects were asked to deliver one repair and can reasonably choose a different issue.

4. **Define each behavior check by what its outcome establishes.** Freeze these classifications for all four arms. Express results as case-level evidence and denominators, with no pooled quality score.

   | Observation | Interpretation |
   |---|---|
   | Submitted selection passes the clean case and detects a credible fault that passed the original selection | Verified added sensitivity when the named assertion reached its intended behavior |
   | A permitted transformation preserves the specified contract | Candidate should accept it. Record an observed rejection as implementation coupling |
   | A separate keeper detects the same independently promised fault under both original and submitted selections | Evidence of preserved sensitivity for that keeper. A clean green run alone leaves sensitivity open |
   | The original already detects the fault in a sibling or stronger boundary | Can support a claim about a weak individual check. Additional suite-level detection remains unestablished |
   | A checker narrows or defers a judgment | Verify its new claim, meaningful remaining judgments, and independently promised behavior. Keep deferral distinct from a correct classification |
   | A runner collected zero tests, skipped the relevant assertion, timed out, or failed during setup | Record the selection and cause. A useful fault detection requires the intended assertion to run and fail |

   Identify the candidate's selected repair independently of the reference patch, command name, path or wording. Include newly added and renamed tests in the candidate's effective selection. Check relevant pre-existing siblings and the native collection or CI route when a claim depends on registration. An independently injected evaluator witness can establish that a fault is real. Credit the submission with detecting it only when its own effective test or checker does so. Treat a refuted finding, an unsupported assertion, and a candidly unverified hypothesis as different results. Count novel verified findings separately. Preserve Phase A's six failure cases and three legitimate controls as separate rows, using its original all-criteria rule. 5. **Make the resource bound operational.** The nominal priority files alone sum to 1,389,078 bytes in Mermaid, 612,733 in Keyboardia, and 750,494 in PDA, before owners, skill text and tool output. A 25-minute audit can support selective search and one focused repair. Link inventories and guides for selective local search. Record total token use as unavailable on an unmetered backend. Pre-stage locked dependencies, run an offline smoke command in an actual fresh subject copy for each case, and document any unavailable runners, history or fixtures equally. Start the 25-minute clock after the usable copy is ready. Record start, deadline and receipt or timeout per subject, outside queue and preparation time. With the final one-subject-per-project limit, four waves can consume roughly 100 minutes of Phase B subject work at full budget, before validation and judging. Reuse read-only dependency material with separate mutable caches and scratch trees. Distinguish host elapsed time, focused runner time and historical CI runtime.

6. **Specify failure disposition and independent validation.** Calibrate each scored control against the pristine original for its expected result and failure reason. Check one feasible reference repair or positive witness and a meaningful keeper for each primary repair path intended for automatic verification. Preserve the original and submitted diff, selected test names/counts, exit, diagnostic and input variant for each evaluator run on a clean copy. Run participant code with an offline, bounded process, minimal environment, and isolated writable locations. Record unavailable execution explicitly. Freeze one rule for deterministic retries of a demonstrably broken harness or transport, applied symmetrically regardless of outcome. Retain each attempt. A new subject answer after a trial starts changes the trial. Distinguish subject timeout, delivered partial work, reproducible patch breakage, absent patch, evaluator incompatibility and platform failure. Report scheduled, returned, usable, executed and judged counts so exclusions are visible.

7. **Define the audit trail and publication boundary.** Seal raw outputs and diffs before judging and blind verdicts before decoding. Judges get the same criteria and matrix, opaque candidate IDs, and prescribed instructions to treat candidate prose as data. Check verdict arithmetic and preserve any disagreement between a judge's interpretation and an executed control. Report the latter as the factual observation for its stated input. Keep reads and commands claimed by subjects separate from controller-observed diffs and reruns. The collaboration backend supplies no centrally audited tool history, provider-attested identity, or measured token totals. Record the requested model/effort, elapsed timestamps and exact artifacts it does supply. Keep the mapping and hidden controls outside subject directories. For any authorized public report, use an explicit file list, public source pins and redistributable evidence. Leave private inventories, workspace credentials, raw environment dumps, local caches and unreviewed third-party material in the private workspace. Retain required notices for vendored source. Strip incidental local paths or identifiers from publication copies while preserving private originals and noting redactions. ## Limits to disclose with the result

The earlier screen yielded 9/9 in each of three arms. Repeating it can reveal a regression or describe a new comparator. A tie leaves incremental benefit unestablished. Keep its plans apart from executed repository repairs. For Phase B, report each revised-versus-PR, unaided, and OpenClaw comparison by case and outcome, including losses, ties, mixed results, and unavailable comparisons. With a single subject per cell, three purposively selected repositories under one owner, seeded anchors and one blinded same-family judge per case, the result describes the observed runs. Source familiarity, phrasing that hints at treatment, shared-host contention and self-reported coverage limit stronger inferences. The four arms had access to different guidance by design. The study measures the package after it is supplied, under the tested workflow and budget. It cannot establish automatic skill discovery, exhaustive whole-suite coverage, repeatability or prevention of the original campaigns in deployment.
